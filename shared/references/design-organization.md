# 项目设计组织模式

组织模式决定后续设计维护哪一份资源。项目只有一处公共 foundation；完整 Spec、组件、说明与场景仍在 requirements/ 维护，HTML 按需重新导出。一个设计资源可以包含多页和候选，持续模式不要求把源码写成一个 HTML 文件。

## 初始化时协助选择

先读 project.json 与已有决定。已有有效选择直接沿用；没有选择时，结合项目真实结构给出推荐、依据及主要代价，由用户确认。用户可以指定模式，也可以明确授权 Agent 根据已说明的依据决定；推荐、默认选中和超时不构成确认。

| 模式 | 适用情况 | 默认处理与代价 |
| --- | --- | --- |
| 产品持续迭代（continuous） | 共享壳层、导航与状态关联紧密，需要在完整产品上下文中评审后续变化 | 更新同一产品主稿的页面、流程与说明，导出同一主稿 HTML；修改后验证关联页面 |
| 按需求独立设计（per-requirement） | 需求边界清楚，需要独立评审、交接或并行推进 | 每项需求独立组织、预览和导出，复用公共基础；分别维护来源与上下文 |

产品大小和组件数量不单独决定模式。持续模式需确定主稿 ID；已有主稿明确承接，没有主稿时可约定 product，开始首项实际设计时再建立。基础验证预览保持验证用途，不充当产品主稿，初始化也不自动开展全部业务设计。

## 保存与读取

用户实际确认后，在 project.json 的 designOrganization 保存 `{ "mode": "continuous", "primary": "product" }` 或 `{ "mode": "per-requirement" }`。缺失或 null 表示尚未确认，不能推断为某种模式。理由与确认来源记入 foundation/design.md；不要将某个使用方项目的选择写入插件通用资源。

通过公共 CLI 保存；命令中的参数应来自已确认决定，不以工具成功代替用户确认：

```sh
node <插件目录>/workbench/cli.mjs init --project <项目> --mode continuous --primary product
node <插件目录>/workbench/cli.mjs organization --project <项目>
node <插件目录>/workbench/cli.mjs organization --project <项目> --mode per-requirement
```

已有工作区使用 organization，不重跑 init。旧工作区缺少该字段时仍可打开现有设计，在初始化或需要确定新设计归属时补充选择，不擅自搬移、合并或重命名既有资源。

## 后续默认与单次例外

每次开始产品到设计的承接、交互、视觉或恢复工作时先读取项目模式及当前设计。持续模式优先更新主稿，新增页面、流程和状态也留在其中，保留其他已接受内容；局部候选比较仍可在同一主稿内进行。按需求模式为新的需求建立独立设计，调整既有需求时继续维护原资源。

持续模式首次建立主稿可运行 new，不传 ID 时使用配置中的 primary；已有主稿直接维护，不重新创建。只有用户明确要求单独设计时才运行 `new <独立设计ID> --separate`。单次例外保持独立，不改变默认模式，也不自动合回主稿；需要承接主稿时记录其来源与边界，合并须有用户明确要求。切换项目长期模式也须有对应的明确决定。

基础验证预览使用 `new <预览ID> --preview`，manifest.purpose 为 foundation-preview；业务设计的 purpose 为 design。--preview 仅用于基础验证，不能借此拆分业务需求。持续模式的主稿不能使用预览用途。CLI 无法判断自然语言授权，调用方必须先取得上述用户决定，再使用对应参数。

工作台默认打开已建立的主稿；主稿尚未建立时可以打开基础预览，不自动把独立设计提升为主稿。工作台 Agent 每轮接收项目模式、主稿 ID、当前设计及用途；当前设计内的身份权限不变，项目设置、新建独立设计及跨设计合并由外部 Skill Agent 按授权处理。

持续模式导出可省略 ID，使用当前主稿及稳定文件名；CLI 通过 --out 选择资源目录外的文件，后续可替换同一输出。按需求模式及显式查看独立例外时使用各自 ID。导出、检查和保存模式都不代表用户验收。
