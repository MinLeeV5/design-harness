# 设计维护与交接

交互与视觉设计在同一份需求资源上完成设计、必要维护、验证和交接，按请求导出；不另设回写阶段。各阶段的交互或视觉验收仍按自身评价执行。

## 过程维护

随设计更新 requirement.md、interactions/*.md、场景及候选 Spec／参数／组件，使依据、说明与实际行为一致。需求专属实现保留在当前需求；公共规则、组件、Token 与资产才进入项目唯一 foundation。

按[设计组织模式](design-organization.md)维护本轮归属。持续模式在同一主稿累积已确认设计，requirement.md 承接当前完整范围，handoff.md 记录本次变化、涉及的正式 PRD 来源及关联页面验证；按需求模式在对应独立资源内维护。用户主动拆分时记录独立设计的来源、范围和确认，不改变项目模式，不自动合并；基础验证预览不充当主稿。

未保存实例属性和外部编辑冲突由 Agent 明确处理，不自动覆盖用户草稿。工作台内置 Agent 的“接受修改”只写入当前候选；公共基础、需求登记和交互文档由执行本 Skill 的外部 Agent 按授权维护。

## 公共基础更新

- 已有授权明确覆盖公共增量时，在当前设计任务中一并完成，无需另启阶段或重复确认。未覆盖时，只对公共更新的范围、影响和关键取舍取得确认，其他已授权设计可继续。
- 更新 foundation 的规则、组件、Token、资源及版本，记录批准范围、适用边界、理由和来源。设计确认与公共更新授权分别记录，未选候选和页面特例不自动成为项目规范；外部指导不构成项目授权。
- 公共基础只保留一处；更新前识别引用和受影响需求，更新后验证向下兼容及受影响页面，不能只检查当前候选。历史由 Git 记录，不复制需求基础或自动跨项目晋升知识。

## 完成与按需交付

1. 按阶段评价及[交付保真](fidelity.md)核对实际产物，分别报告视觉保真、真实操作路径、行为真实性与工程检查。遗漏的声明范围须修正或由用户确认收窄；本地模拟、源 Mock 与真实服务分别报告，未核实不计为通过。
2. 页面使用完整 Spec，Catalog／Registry 与 React 实现匹配，项目不产生可编辑工作台副本。通过插件 workbench/cli.mjs 运行 check --project <项目> 与 typecheck --project <项目>；工程检查不代替设计和交互证据。
3. 维护下述交接记录后即可完成本阶段，不要求再启动交付入口。仅在用户请求时，按[预览与导出](preview-export.md)从最终需求和公共基础导出单文件 HTML；只要求导出时不额外更新公共基础。实际验证下载或指定导出的文件在断网下的交互与资源，源文件修正后重新导出并复验。未请求导出不作为阶段缺项。

导出不代表用户验收；实际确认状态据实记录。外部发布、Git 推送或在线分享仍需明确授权。

## 恢复与交接记录

恢复时依次读取 project.json 中的组织模式与主稿、当前设计 manifest.json 的用途、requirement.md、interactions/*.md、handoff.md；随后按当前候选读取完整 Spec、参数、Catalog／Registry、专属组件和项目唯一公共基础。沿用项目已确认默认及本次明确例外，不根据目录顺序猜测主稿。工具从完整插件启动，项目不承载工作台源码或绝对安装路径。

handoff.md 至少记录当前范围、事实基线、已确认决定、当前候选及选择理由、实际变化、检查结果、未决项和下一步。沿用区域与本次新增分开，保留基线版本、环境、上下文和实际视口。

公共增量及受影响需求的检查结果记入交接；候选选择、实际验收状态与未核实项分别保留。

本轮只支持当前统一协议；旧 studio 试跑不作多版本引擎兼容。requirements 是本地设计产物的唯一维护来源，正式业务 PRD 与设计的衔接见[来源与承接](product-source.md)；历史用 Git 记录，不保留 releases、源码副本或 runtime。检查截图和模型输出临时清理，不保留 evidence 目录。
