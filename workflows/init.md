# Init：整理现状，再补齐缺失

本流程不要求用户填写项目配置文件。工作结论先在对话中审阅，再写入项目 Figma。

## 1. 建立读取范围

从已提供的 Figma URL、仓库、工作区和对话中确定项目。只读检查：

- Figma 的 Page 列表、用户指定的历史页面、已有 Harness 入口及相关资产；先看结构，再选代表节点。
- 仓库 AGENTS/README、架构与设计文档、相关 UI 模块、资源、主题与状态分支。用搜索定位，不整仓读源码。
- 当前分支和 revision；工作区改动若影响结论也需注明。产品渠道、平台和目标屏幕不同的实现不可混为一套规范。

Figma 缺失的事实继续从代码查；需要用户决定的仅是实际取舍、范围或无法查询的意图。相关源码不可读取时，说明只能完成哪些整理，不能把猜测作为实现事实。

识别已有 Harness、需求 Page、待实现设计以及已有确认。若缺少 Harness，拟定独立 `design-harness` Page、入口及模块布局；将这份具体方案并入第一个模块的确认，不提前写一页空模板。用户已经指定目标 Page 时复用它。

## 2. 阶段一：逐模块整理存量

按依赖关系依次处理项目上下文、设计风格、Tokens/变量、布局、组件、模板、场景；可根据项目调整顺序，不能遗漏依赖。每次只对当前模块生成可审阅提案：

| 展示内容 | 要达到的程度 |
| --- | --- |
| 拟沉淀内容 | 列出具体规则、代表资源、适用范围、来源和当前状态，不能只说“整理组件” |
| 冲突与缺口 | 区分原稿已有、代码已有但原稿缺失、已确认待实现、证据不足 |
| 推荐取舍 | 对冲突说明推荐依据与影响，尤其是代码较新、渠道不同的情况 |
| Figma 呈现 | 说明拟用的原稿标题/分组/场景连接方式、承载节点、复制还是新建 |
| 本次写入 | 明确哪个 Page/模块/文件级资产会变化；缺失补齐列为阶段二计划 |

按 [模块标准](../references/init-modules.md) 给出实质内容。**该模块确认后**再组织存量资产与索引。用户提出修改就调整该模块；不要把“开始 Init”理解为认可所有模块内容。

对于能在代码核实的差异，先调查再推荐，不把调查任务转交给用户。可以在审批某模块时继续只读盘点其他模块。

每次写入后回读真实节点、核对来源链接与截图，更新该模块概览和入口状态。使用实际生成的节点 ID，不为未生成的资源伪造链接。中断时，在对话中报告最后完成的模块；新会话可由入口和模块状态恢复。

全部适用模块的现状与差异整理完成后，再进入补齐；若用户只要求部分模块，以该范围为准。

## 3. 阶段二：补齐代码已有而 Figma 缺失的内容

根据阶段一的缺口，按依赖顺序补齐（通常先 token/布局，再组件、模板和场景）。逐模块提出实际要补什么、按哪些代码与状态重建、怎样呈现，**确认后生成**。

如果阶段一用户已明确批准同一项具体补齐内容及写入范围，引用该确认继续，不再重复问。只同意“记录现状”不等于同意所有推导出的新规范。

- 代码中的组件：重建原生可编辑组件、必要变体和内容属性；绑定已批准变量/样式；保留源码映射。
- 代码中的状态：核对触发条件和恢复路径，补齐相关组件状态或场景状态，不能只补一张截图。
- 代码中的规律：从可复核的重复用法提出命名和规则，不从单个硬编码值臆造规范。
- 无运行环境：可按源码重建并标明“代码已实现／静态核对”；不要声称与实际运行像素或行为一致。
- 代码也没有的设想：标为待决策的新需求，不混入“补齐已有实现”。已确认设计则按其确认记录维护。

每模块使用 [检查标准](../evaluation/checks.md) 检查资产类型、变量绑定、变体、布局、来源和实际渲染。缺陷能在授权范围修正就修正；新取舍回到该模块确认。

## 4. 收束与增量更新

检查入口→模块概览→资源→来源链路是否可读取，以及未完成状态是否准确。给出 Harness 链接、已完成/暂缓部分和下一次 Design 的调用方式。

再次 Init 时按 revision、节点与模块状态比较变化；只更新受影响资源与引用，不整页重建。保留稳定资源标识与原有链接。若源节点消失或语义改变，修复索引；不要默认同名资源等价。

当前代码与“已确认设计／待实现”不一致，通常意味着尚未实施，而不是设计无效。按 [知识更新规则](../references/knowledge-update.md) 检查是否存在明确取代关系，防止倒退覆盖。
