# 具体增量与执行顺序

## 可审阅的提案

用 [增量蓝图](../assets/writeback-delta.txt) 列出真实前后变化、来源设计与确认版本、适用平台/任务、目标节点或文件级资产范围、依赖影响和状态。一个主方案无需额外多方案选择；没有可复用变化，只提出需求索引或不回写。

用户批准设计不等于批准未展示的全局规则。已明确批准的同一增量直接执行，仅对新增范围补确认。新 Library 来源、图标家族、插画风格及设计语言章节只转写已确认的内容；不在此生成新规范或重新选择设计方向。来源登记不授权订阅、发布或改写源库。

## 状态与契约

- 当前实现、候选设计、已确认待实现、已确认已实现分别保留；只有核实落地后才能改实现状态。
- 设计状态、用户确认与验证结论不是一个通过标记。静态源码检查、Figma 连接回读、预览体验与产品运行各有证据范围。
- 资源说明按 [资源蓝图](../assets/resource-card.txt) 写用途、范围、真实资产、规则、依赖和确认；必要时简述待验证事项。视觉意图与精确 token 的关系从已确认设计转写，缺失就列待定。
- `DH / Module` 只索引稳定资源 ID、用途、说明 TEXT 节点和状态；`DH / Entry` 保留项目边界、全局约束、一条仓库链接及模块、需求与已确认待实现索引。具体行为归布局、组件或场景，项目上下文保留概览。
- 使用 [文档约定](work-templates.md) 保持可见原生 TEXT 的层级与真实定位；不加入源码路径、符号、commit、调查日志或隐藏正文。

## 更新

1. 按 [读取约定](context-loading.md) 查现有稳定资源和依赖。新规则影响当前实例时，默认保留可辨版本或变体；原位替换必须在批准范围内。
2. 整理已批准的真实资产与说明，再更新模块与入口引用。使用实际返回的节点/变量/样式 ID，不为计划中的资产建假索引。
3. 复制或移动组件先核对依赖与实例关系；不要假设 clone 自动迁移引用。源稿、团队库和文件级资产各自核对授权。
4. 按 [回写检查](evaluation.md) 回读内容、状态、链接、绑定及截图。部分失败先查已完成结果，只补缺项；本阶段 [交接](handoff.md) 列明实际完成、暂缓及待验证。

已确认待实现的新设计不能被旧代码倒退覆盖。后来代码落地时，由用户另行启动适用模块的增量整理，本阶段不自动继续。
