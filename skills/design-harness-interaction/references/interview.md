# 交互访谈：一次一个关键问题

先从已有项目约束、交付物和相关代码查事实；不要把可查询的状态、尺寸或资源位置反问给用户。模糊目标从用户任务与受阻位置开始，成熟方案继承历史决定，局部修改只检查受影响范围。

每轮选择当前最影响方向的一项不确定性：简述已知依据，问一个问题，给出推荐及理由。选项体现真实取舍；用户回答后记录实际选择及影响，不把沉默、模糊回复或 Agent 建议当作批准。没有必要把每个按钮、图标和已委托细节都升级为决策。

| 当前步骤 | 访谈重点 |
| --- | --- |
| 整体需求和骨架 | 用户、任务、入口/结果、范围、参与端与主分支关系 |
| 主流程 | 当前操作、跳转、返回和关键反馈，展示可点击片段再确认 |
| 当前分支 | 触发条件、恢复/退出及与主流程的连接；确认后再选下一条 |

可以用标注为讨论稿的文字线框、流程图与局部草图辅助取舍。正式写入前承接或取得整体需求确认；明确授权提前写入某个草图时只执行该范围，不推定正式方案获准。

对话中维护已核实事实、已确认决定、明确委托及未决事项。到实际确认和交付检查点，将恢复必需的部分写入 [交接记录](handoff.md)，不要求本地 brief、run.json 或完整访谈日志。新任务从记录和真实产物恢复；只对缺失、冲突或新事实影响的决定补问。

目标、边界、主路径和必要分支足以支撑当前原型时停止扩展问题，先交付可审阅片段。交互稿完成后结束本阶段，不延伸到视觉方向访谈。
