# 交互共创：一次讨论一个关键问题

在流程、当前页面、分支、状态和串联评审中使用。先从项目约束、真实交付物和相关代码查事实，承接历史决定；可查询的状态、尺寸或资源位置不反问给用户。访谈可以连续多轮，每轮只问一个问题，给出推荐及理由，并等待回答。

## 本项的讨论循环

1. **回述任务与理解**：说明当前用户想完成什么、本项怎样承接前后步骤，展示已核实依据或当前实际稿。模糊目标先探索受阻情境与成功标准，不直接要求用户批准一条 Agent 自拟流程。
2. **选择关键取舍**：检查操作顺序、信息出现时机、反馈、返回/退出或恢复方式是否有未决判断。指出具体位置及对用户的后果；问题围绕产品行为，不只问下一步是否制作某页。
3. **提出一个问题**：给出可行方式的收益与代价、推荐及依据，再问一项取舍。尚需理解情境时使用开放问题并说明初步判断，不把 Agent 的备选当成全部可能性。可在获准范围用文字线框、流程图或局部草图帮助讨论；实际备选稿仍遵守 [逐项门禁](handoff.md#交互与视觉的逐项门禁)。
4. **反馈改变方案**：简述用户回答对当前流程、操作或状态的影响；明确的修改在当前授权范围落实。回答只表达困惑或原因时继续澄清这一问题，不把它归为认可、也不急着问下一页放行。多个未决项按影响逐题处理。
5. **展示并收束本项**：展示讨论后修订的实际稿，说明采用的决定、理由与变化。有新的关键问题则继续本项讨论；足以判断当前稿后，再合并询问该版本验收与一个具体下一项放行。下一项若另有未决行为，先讨论它，再提出制作计划。

每个制作或评审检查点都检查关键取舍。已有决定充分时，简述沿用哪些规则及理由，直接执行本项或进入验收，不为每页凑访谈题。用户已委托的常规细节在当前项内处理。

## 按当前步骤定位讨论

| 当前步骤 | 共创重点 |
| --- | --- |
| 流程与关键草图 | 用户任务、成功标准、入口/结果、参与端责任、主分支关系；先共同确定流程，再讨论获准草图 |
| 主流程当前页 | 本页信息与操作的先后、跳转和返回、最小反馈；结合实际稿检查是否符合任务 |
| 主流程串联 | 用入口到完成的任务情境检查跨页理解、连续反馈与退出；逐页认可不能代替整体判断 |
| 分支或单页状态 | 触发时用户知道什么、需要保留什么、怎样恢复或退出，以及与主流程的连接 |

例如，失败态的关键问题可以是“失败后保留输入以便重试，还是重新开始”，先根据用户任务说明推荐与代价。答案改变恢复规则后再讨论当前稿；不要只报告“下一步制作失败态，可以吗”。

## 讨论、验收与放行

取舍回答只确定对应行为，未展示的修订稿仍待验收；没有已说明的下一项计划，也不能从“按推荐做”推定下一页获准。用户同一回复已明确验收具体版本、放行具体下一项时直接承接，不重复审批。只要求修改就只修当前项；影响上游已确认行为时按 [阶段边界](handoff.md#阶段边界) 提出问题，取得相应修订范围。

按 [交接约定](handoff.md) 保存关键问题、真实结论及理由、方案变化、仍未解决的内容和本项验收/下一项放行；不保存整段访谈。恢复后从未完讨论继续，不重访已确认内容，也不只重发下一步计划。交互交付后停止，不延伸到视觉访谈。
