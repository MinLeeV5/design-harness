# 交互工作流

1. 读 project.json 的[设计组织模式](../../../shared/references/design-organization.md)、当前设计、交接、项目共享基础及必要实现事实；指定正式业务 PRD 时按[来源与承接](../../../shared/references/product-source.md)核对并记录设计依据。按[交付保真](../../../shared/references/fidelity.md)明确用户任务、交付范围、来源基线及可观察验收条件。
2. 关键分歧逐题共创；已有决定直接承接。持续模式的新需求默认在产品主稿内累积，保留既有页面和已接受行为；主稿尚未建立时创建配置中的主稿 ID。用户明确指定或已打开独立例外时继续维护该设计，不因项目默认而合回主稿。按需求模式为新需求建立独立设计，调整既有需求时维护原资源。只有用户明确要求单独设计时才用 --separate 创建持续模式的例外，不改变项目默认或自动合回主稿。旧项目模式未确认且需确定新设计归属时，先协助确认。采用[文档协议](../../../shared/references/protocol.md)，登记页面、适用的产品壳层、状态及明确排除项。
3. requirement.md 记录目标、范围和验收；interactions/*.md 按[交互协议](../../../shared/references/interactions.md)独立记录正文、页面归属、状态条件及标注模式；完整 Spec 组合页面，Catalog／Registry 注册 React 组件并实现可操作流程；scenarios.json 仅登记体验初始状态。路由与可观察状态接入工作台 SDK，实际跳页后同步顶部和说明。复杂流程可补 Mermaid，不强制另做静态线框。
4. 复用项目共享基础；沿用区域保留实际入口、控件和菜单层级，交互与视觉共用 Spec 与组件。获准的公共基础增量按[共同维护与交接](../../../shared/references/handoff.md)在当前任务中完成，并验证受影响需求。未实现的服务行为在评审说明中明确本地模拟，不连接业务服务，也不因此省略已声明的 UI。
5. 在工作台使用首次默认的“交互设计”身份（有记忆时按需切回），读取同一工作流并承接当前需求、交接、完整说明和实际状态；提出修改时将页面、说明、场景和登记作为同一提案，核对影响范围及所有候选，接受后统一写入。在[预览](../../../shared/references/preview-export.md)中从真实入口体验主流程、分支、菜单／弹层、校验、键盘、固定与滚动区域以及恢复；区分可到达路径和仅预置场景。完成范围内必要页面和状态，不逐帧请求许可。
6. 展示实际产物与分项证据，处理反馈并按[共同维护与交接](../../../shared/references/handoff.md)完成检查和交接；请求导出时一并生成、验证离线 HTML。完成交互评审后停止，视觉细化由用户另行选择。

关键分歧只比较对应局部；明确改动直接落实。公共基础更新、交接和按需导出均在本阶段内处理，不依赖另一个 Skill。

工作台可为同一候选创建独立并发会话；上下文和待确认提案归属当前会话，其他会话生成的内容不代表已接受。切换不会取消任务，文件冲突由用户协调；遵循[会话并发边界](../../../shared/references/agent.md)。

工作台执行按[专业 Agent 权限与审批](../../../shared/references/agent.md#权限审批与执行过程)选择只读分析、提案工作区或完全访问。默认提案接受后写回；完全访问可能提前改源，放弃或取消不回滚。审批与执行过程在所属会话核对。
