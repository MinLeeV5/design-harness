# 交互设计：主流程优先

按 [交接约定](handoff.md) 恢复本次需求；只读当前步骤的项目依据与参考。阶段输入是用户目标、相关项目约束和已有决定；缺失事实先查，影响方向的取舍按 [访谈](interview.md) 一次问一个。

## 1. 确认范围与流程骨架

明确用户、任务、入口与完成结果、参与端、主要状态、主路径、必要分支和不做的部分。先用流程图与少量说明呈现骨架，必要草图标为讨论稿；用户整体确认后才生成正式需求 Page 与原型。成熟需求直接承接既有确认，小改动只处理受影响片段。

每次需求使用独立 Page，已有则复用；按 [需求蓝图](../assets/requirement-page.txt) 只建立本阶段需要的区域。分支先登记触发条件与优先级，不并行铺开所有分支稿。页面权限不等于文件级变量、主组件或原稿的修改权限。

## 2. 完成主流程

按 [原型制作](prototyping.md) 做从真实入口到任务完成的可点击低保真稿，覆盖必要操作、反馈和返回/退出。复用适用项目组件与现有画面，保留真实信息和操作尺寸；用可编辑示意图帮助判断，不加载插画生成或视觉精修流程。

默认一套主方案。关键交互有分歧时，仅比较对应片段，展示可体验产物后继续逐题确认；选定后并回主线。按 [检查](evaluation.md) 回读原型连接，实际点击能力及结果单独报告。主流程交互获确认后，更新交接记录再处理分支。

## 3. 逐条完成分支

每次选一条已纳入范围的分支，确认触发条件、操作/反馈、恢复或退出、与主流程的连接。制作并走查这条分支，用户确认后再开始下一条；已明确委托的细节直接处理。暂缓、不适用和待验证分别记录。

分支暴露主流程冲突时，先给出受影响决定、原因和建议；由用户决定是否重开该决定。只修订批准范围并复核依赖，不自行修改其他已确认路径。每个检查点更新本阶段记录，压缩后从当前分支继续。

## 4. 交付并停止

交付流程骨架、主流程与适用分支的原型入口、确认范围及必要验证限制。记录已确认的产物版本和未完成项；不能把主流程确认当成全部分支确认，也不能把静态图当成可点击原型。

用户可在知道验证限制后确认方向，或明确缩小交付范围；保留真实限制。交互就绪后建议用户在新任务调用 `$design-harness-visual` 并提供本次交接链接，**本阶段到此停止**。不细化正式视觉，不更新 Harness 全局知识。
