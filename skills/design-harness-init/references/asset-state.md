# 资源状态与增量对齐

用于 Init 盘点、补齐和再次对齐时判断哪些知识仍有效。Figma 分别表达设计状态与实现状态，必要时简述验证限制，格式见 [资源蓝图](../assets/resource-card.txt)。源码版本和核查过程留在当前任务中。

| 发现的事实 | 如何记录与处理 |
| --- | --- |
| 当前代码可以核实的行为 | 现状基线／已实现；注明适用平台/渠道，仅静态核实时说明相关行为待实机验证 |
| Figma 中未经确认的方案 | 候选设计；保留来源，不作为项目默认规则 |
| 用户已确认而代码尚未落地的设计 | 已确认设计／待实现；保留确认范围和来源需求 Page |
| 后续代码实现了已确认设计 | 核实对应行为后改为已实现；必要时保留待验证事项，不能只凭同名文件或时间推断 |
| 证据不足、范围不清或已被取代 | 明确未核实，或指向有效版本；保留必要历史依据 |

当前代码用于还原现状。它与“已确认设计／待实现”不一致时，先检查目标版本和确认范围，不能把未实现设计倒退成错误稿。新设计是否取代旧规范必须有实际确认依据；不能伪造审批记录。

## 增量更新

1. 根据稳定资源 ID、源节点与适用范围定位已有内容；需要判断实现变化时再查源码版本。移动节点不改变资源语义 ID；同名不代表同一资源。
2. 比较新证据与原记录，区分事实变化、设计取舍和未实现差距。对需要取舍的冲突提出具体建议，再按当前模块确认范围执行。
3. 涉及新资产或规则时，展示前后变化、目标位置、影响与状态。先建立实际资产，再更新资源说明、模块目录与入口；使用真实返回 ID。
4. 保留当前实现与已确认未来设计各自的来源。修改现有主组件或文件级变量前核对影响范围，不能让整理操作改变未授权原稿。
5. 依照 [Init 检查](evaluation.md) 回读资产、索引、状态与依赖。中断或超时后先核对实际结果，只继续缺项，避免重复创建。

Init 不重新评选需求候选方案。需求的选择和具体沉淀范围以真实用户确认记录为依据；没有这些记录时保留待确认状态，不能自行将候选稿提升为规范。
