# 七类模块的产出标准

本表用于逐模块提案与检查，不是要求每个项目套用同一种版式。先观察原稿的标题、分组、注释、箭头和场景排序，提出本项目的呈现方式。对于不适用项说明理由，不虚构一个“完整库”。

## 1. 项目上下文

- 说明产品、角色、主任务、平台/渠道、设备尺寸、输入方式、环境和业务边界；用实际设计与代码支撑。
- 建立仓库/版本、Figma 来源范围、语言与术语、明确排除范围的索引。继承用户指定的历史 Page 范围，不顺便扩扫其他项目。
- 给入口提供简明全局约束与模块目录；详细业务规则留在相关场景资源。
- 代码存在多个渠道/布局时，记录共同规则和差异，不把某个渠道当作全部产品。

**补齐**：将代码已存在而原稿未说明的角色限制、渠道边界或业务条件加入上下文。未知意图留给用户决定。

## 2. 设计风格与约束

- 从代表性原稿与当前主题代码提取字体、信息层级、密度、图标、形状、色彩语义、反馈和动效原则。
- 区分重复稳定规律与局部特殊情况；展示来源和正反例。冲突逐条给出倾向代码的建议，但保留用户取舍。
- 输出可执行的使用原则，例如主次操作、危险/禁用表达、内容优先级；不能只有“简洁、现代”形容词。

**补齐**：加入实现已有的交互/文案/渠道例外。通用审美建议不能覆盖项目身份。

## 3. Tokens 与变量

- 盘点 Figma 变量/样式和代码资源/主题：原始值、语义名、使用处、模式/渠道、来源和冲突。
- 提案说明复用哪些已有资产、新建哪些项目命名空间，及批准范围内是否需要调整绑定。
- 创建实际可用的变量与合适的样式；保留语义到原始值的别名关系。字体组合等不适合单个变量的属性用文字样式/规则承载，不强行“一切变量化”。
- 展示颜色、字体、间距、尺寸、圆角等实际使用样本；只有出现可靠语义时才增加层级。

**补齐**：以代码已有值为依据补命名、模式和状态用法。检查真实绑定、别名解析、不同模式值；色板截图或表格不是变量库。

## 4. 布局

- 提取画布尺寸、区域划分、栅格、边距、对齐、弹性/固定尺寸、安全区、溢出及缩放规则。
- 区分页面骨架与组件内部布局，展示典型长文本、多内容及状态变化。
- 用可编辑 Frame/Auto Layout 或项目确有依据的固定布局表达；只有在需求/实现支持时增加响应式行为。

**补齐**：把代码已有但原稿不全的空间分配、滚动、截断、输入法或窗口变化规则补成带条件的规范。

## 5. 组件库

- 按交互职责及复用程度归类，建立原生 Component/ComponentSet、内容与状态属性、实例及变量/样式绑定。
- 覆盖实际实现的必要状态：例如默认、按下、选中、禁用、加载、错误，依组件用途选择；不要机械制造全部状态组合。
- 资源说明写清属性、触发条件、内容边界、组合方式及源码路径/符号/版本。提供代表实例检验复用。
- 原稿只是 Frame/截图时如实分类为参考；经确认转换或重建后才称为组件。已有组件使用实例；克隆/重建组件时核对内部实例、变体和绑定，没有授权不能改动原始主组件。

**补齐**：从实际组件实现恢复遗漏的属性、状态和布局，生成真正可复用资产。索引、命名“按钮”的普通 Frame 或截图不能宣称完成组件库。

## 6. 模板库

- 模板按可复用的**页面结构/交互模式**挑选，不按原稿截图数量一一复制。例如列表+详情、引导步骤、空态承接。
- 同骨架的不同文案/状态/业务实例通常共享模板；导航、区域结构或任务模式确有差异才独立建模板。
- 每个模板说明适用任务、结构槽位、可替换区域、状态扩展、依赖布局/组件和代表性场景。
- 提供可实例化的组件或可复制编辑的 Frame；明确其复用方式。关键区域实际复用组件与变量，不能只是整屏贴图。

**补齐**：代码新增了结构不同的页面模式才扩充模板；仅状态变化补到对应模板的状态说明和场景库。

## 7. 场景库

- 场景按用户任务、入口条件、步骤、分支和结果组织，覆盖本范围的不同业务情境。
- 用原稿习惯的场景标题、箭头和注释串起流程，保留原稿来源链接；明确输入、反馈、退出/返回与失败恢复。
- 一个模板可以支持多个场景；一个场景也可能串联多个模板。建立双向索引，避免用少数模板代表全场景已覆盖。
- 代表画面用于说明场景，完整原稿参考按需要链接/复制，不要求每次全部加载。

**补齐**：把代码存在而 Figma 没有的分支、状态与恢复补成可读的流程和画面。设计新增的想法先走 Design，不冒充历史实现。

## 模块完成的共性

真实内容、适用范围、来源、状态、稳定 ID 与可读取定位齐全；目录与资产一致；相关依赖可按需找到；实际渲染符合项目展示习惯。用户确认的是明确内容，不能用“已批准模块名称”代替对实际方案的确认。
