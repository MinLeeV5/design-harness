# Init 共创：逐模块理解、讨论与修订

在整理或补齐每个模块时读取。先查项目事实，再与用户共同确定知识的含义、适用边界和呈现方式；沿用已有确认。访谈可有多轮，每轮只问一个影响当前模块的问题，并给出推荐与理由。

## 当前模块的讨论循环

1. **回述理解**：用产品语言说明本模块要帮助谁解决什么问题，展示少量代表资产或具体规则。区分已核实事实、已确认意图和待核实推测，不只报告下一步会整理什么。
2. **找出关键取舍**：检查规则的适用范围、例外、复用边界或冲突是否尚未确定。可查询事实先自行核实；不要把代码中的数值、状态或资源位置转成访谈题。
3. **逐题讨论**：说明这项取舍会影响哪些内容，给出可行选择、各自代价及推荐理由，然后问一个问题并等待。意图尚不清楚时先围绕用户任务或使用情境开放提问，不急着把答案限制为 Agent 的两个方案。
4. **承接反馈**：简述回答如何改变模块的范围、规则或呈现，修订当前提案。用户指出原因但未形成决定时，继续讨论这一问题；还有影响当前提案的缺口则下一轮只问其中一项。
5. **形成具体提案**：取舍足以支撑当前内容后，按 [模块标准](modules.md) 展示修订后的规则、代表资源与实际写入范围，再取得或沿用该具体提案的确认。讨论中的偏好不等于写入批准；同一回复已明确批准具体内容与范围时直接承接。

每个模块都检查是否有需要共创的判断；已有决定足以支持本项时，说明沿用什么及理由，直接进入具体提案确认，不凑问题或重访已确认意图。不能把“是否开始整理这个模块”当作已完成访谈。

## 按当前模块选择问题

以下是定位讨论的线索，不是逐条问卷。推荐必须结合当前项目的实际依据。

| 模块 | 需要共同判断的内容 |
| --- | --- |
| 项目上下文 | 主任务与成功标准、渠道责任、业务边界；实现能力不能独自证明用户最看重什么 |
| 设计风格 | 已有视觉规律服务什么任务，哪些是长期原则、哪些是历史或局部例外 |
| Tokens/变量 | 可靠重复用法的语义与适用范围，渠道差异应分开还是共用规则；数值先查 |
| 布局 | 已核实的骨架适用于哪些内容与环境，哪些溢出或尺寸变化属于例外 |
| 组件 | 控件的复用职责、内容与状态边界，现有变体是通用规范还是特定场景用法 |
| 模板 | 页面是否支持同一种用户任务，哪些区域可替换、哪些结构决定独立模式 |
| 场景 | 哪些已实现路径应作为代表，哪些异常/恢复需要独立说明及其使用情境 |

例如，发现多个渠道使用相似布局时，先展示已核实差异，再讨论是否以共同骨架加渠道例外表达；不要只询问“下一步整理布局，可以吗”。用户希望的行为与当前实现不同，保留当前实现事实，另记待决策的新需求或已确认待实现设计，不在 Init 中直接改造产品。

## 写入后的反馈与恢复

展示真实模块和代表资产，说明它们怎样体现已讨论的规则。用户反馈揭示新取舍时继续本模块讨论，在批准范围内修订；本项制作错误直接修复。下一模块按自己的依据与未决项展开，不把当前模块认可当作全部模块的决定。

按 [交接约定](handoff.md) 保存关键问题、实际结论与理由、提案变化及仍未解决的内容，不复制访谈全文。恢复时继续未完成的讨论或具体提案确认，不只重发下一步计划。
