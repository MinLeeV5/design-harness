# Design Harness · 工程实现

由用户显式启动，承接当前任务的范围、授权与已有决定，将指定设计落实到目标项目。实施遵循目标项目已有开发流程；仅讨论或分析的任务保持只读。

design-harness 提供 UI/UX 依据，目标项目决定实现技术、代码组织和工程约束。设计可由 React 与 json-render 表达，目标可为 Web、Android、iOS、桌面或其他具有界面的工程。设计源码用于理解体验，实际实现按目标工程组织，无需建立源码或组件的逐项对应关系。

本阶段聚焦界面结构、视觉、交互、状态及与既有业务能力的连接。原型中的示例数据和模拟行为不直接构成业务契约；缺失能力先按目标项目流程明确需求与技术方案，再确定实现范围。保真策略由目标项目开发者选择，不预设偏向设计或既有 UI。

按[工作流](references/workflow.md)承接设计、调查工程并实施；资料定位与事实依据见[来源](references/sources.md)。遇到保真策略待定、跨平台差异或缺失业务能力时，读取[差异与适配](references/adaptation.md)；已有有效决定直接承接。完成前按[评价](references/evaluation.md)核对目标工程的实际产物、验证结果和剩余差异。

设计预览使用完整 Design Harness 工具包的[公共 CLI](../../workbench/cli.mjs)，工具包目录为本文件所在目录的 ../..。在设计所在项目上下文通过 skills 定位实际采用版本的指导，项目本地版本优先。目标工程的运行依赖、编码方法和验证工具从该项目获取，不要求统一框架或特定开发 Skill。

本阶段在范围内的实现、适用验证和交接完成后停止。设计源维护与工程实现分别按对应任务授权推进；后续动作按用户选择及目标项目流程处理。
