# 差异与适配

仅在保真策略尚未明确且影响实现、存在跨平台差异，或设计依赖缺失业务能力时读取相关部分。

## 开发者选择保真策略

策略由目标项目开发者决定，可在调用时指定，也可沿用同范围内仍有效的选择。常见方式包括：

| 策略 | 实施与验收依据 |
| --- | --- |
| 设计优先 | 在项目技术约束内，优先实现选定设计的视觉与交互；按设计核对差异 |
| 项目 UI 规范优先 | 使用项目既有组件与界面规范，明确设计的适配结果；按项目规范及确定的体验要求核对 |
| 按区域指定 | 开发者明确各区域的策略及边界，分别核对，不自行划分偏向 |

不自行设定默认策略。已有有效选择直接复用；策略未明确且实际差异会改变实现方式或验收结果时，说明具体差异、推荐做法与代价，请开发者选择。没有实质差异时不制造选择题。

策略同时约束实施和验收。项目明确的强制工程约束持续适用；所选策略需要偏离这些约束时，按目标项目机制处理对应冲突。

## 跨平台与框架适配

将信息结构、操作意图和状态反馈落实为目标平台的布局、组件、导航、输入及状态机制。尺寸、字体、资源和交互采用该平台的表达方式，在实际容器中校准，不把 Web 尺寸或事件机械替换成原生单位与事件。

按实际触点处理手势、系统返回、键盘、安全区域、可访问性及生命周期。保留目标项目职责边界，设计预览与业务运行保持独立；业务工程依赖由项目需要决定，不因原型技术而引入其运行器或渲染依赖。

局部细节按现有范围与策略自主决定。适配将改变关键视觉结构、操作路径、状态语义或职责边界时，只对变化部分重新对齐，并记录适配理由与验收方式。

## 缺失业务能力

设计出现目标工程尚未具备的能力时：

1. 核查已有需求、技术方案、接口与实际代码，区分确实缺失和当前尚未接入。
2. 按目标项目既有流程明确缺失能力的需求与技术方案，不从示例数据或模拟行为推导业务契约。
3. 根据明确后的结论、任务范围与授权确定本轮实现内容，范围未定前不执行依赖该决定的动作。

需要占位、测试替身或阶段性交付时，遵循项目约定并明确用途、限制与剩余工作。不依赖未决问题的已授权工作可以继续；模拟效果不计为真实业务能力完成。
