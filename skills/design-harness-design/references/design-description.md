# 设计语言描述 · 参考 DESIGN.md

整理、读取或修订项目设计风格描述时加载。本文与 [内容蓝图](../assets/design-description.txt) 参考 [google-labs-code/design.md](https://github.com/google-labs-code/design.md)，为 Figma Harness 改写；适配部分采用 Apache-2.0，见 [许可证](../third-party/design-md/LICENSE) 与 [来源及修改声明](../third-party/design-md/NOTICE.md)。

## 先读当前上游，再结合项目

首次编写或修订这类描述时，读取上游默认分支的 [格式说明](https://github.com/google-labs-code/design.md/blob/HEAD/docs/spec.md) 与 [写作理念](https://github.com/google-labs-code/design.md/blob/HEAD/PHILOSOPHY.md)，同一任务可复用已读内容。仅使用已确认的项目描述时直接按项目依据读取。按需从上游 README 定位示例；不固定版本、不安装其 CLI。获取失败时说明未取得最新内容，本地适配不是上游规范快照。

采用其核心分工：**精确值提供依据，正文解释设计意图、适用方式和边界**。风格说明应让接手者理解如何延续这个产品，而不只是得到一份数值清单。已确认的项目规范和工作方式优先，不照搬上游示例的品牌、字体、配色或 Web 单位。

## 内容如何写

按以下顺序组织适用章节；标题可用中文，未知内容明确待核实，不适用项说明理由。项目确实需要图标、动效、声音等补充章节时保留，不为填齐目录虚构规则。

| 章节 | 应解释的内容 | 对应项目依据 |
| --- | --- | --- |
| 总览 Overview | 服务谁、什么场景；具体视觉特征与期望感受，以及这些特征如何支持任务。引用已核实的代表画面或明确的风格参照，避免只写“简洁、现代、高级” | 项目上下文、代表原稿、已确认原则 |
| 颜色 Colors | 主色、强调色、背景、正文及状态色各自承担什么角色，如何组合、何时限制使用；名称和数值要能对应 | Tokens/变量的稳定资源、模式与真实 ID |
| 字体 Typography | 标题、正文、标签/数据的阅读职责，层级、字重、行高等选择如何影响信息密度与语气 | 文字样式、字体资源和相关 token |
| 布局 Layout | 内容如何分区，阅读/操作顺序，留白和密度的用途，不同平台或尺寸下哪些规则变化 | 布局资源与产品页面模板 |
| 层次与纵深 Elevation & Depth | 通过背景、边框、遮挡或阴影表达哪些关系，弹层/浮层怎样区分；扁平风格也说明其分层方式 | 表面/阴影规则、布局及状态示例 |
| 形状 Shapes | 轮廓、圆角、边框与图标形状的共同语言和适用边界 | 相关 token 与代表组件 |
| 组件 Components | 控件的视觉职责、主次关系、必要状态和组合方式，哪些变化仍属于同一设计语言 | 已有组件/变体/说明节点；详细规格按需链接 |
| 应当与避免 Do's and Don'ts | 少量能据此作出判断的正反例，附具体触发条件、理由与例外 | 已确认规则、真实例子和来源 |

每节先说设计判断，再写用途与理由，最后给相应 token/资源/代表画面；重要例外紧随对应规则。能从原稿或代码确认的事实直接核实；推测的设计意图标为待确认，不能冒充原作者动机。

例如可以描述“高密度工作台以对齐和分区帮助用户连续比较数据，强调色集中在当前主要操作；具体色值和间距见关联资源”。它说明视觉选择如何服务任务；是否适用于项目仍要有来源与确认。

## 在 Figma 中如何承载

- 设计风格模块的 `DH / Module` 链接稳定资源 `style/design-description`，使用可见原生 TEXT `DH / Resource` 承载，显示标题可为 `DESIGN.md · 项目设计语言`。这是项目设计语言说明，不新增第八个模块或强制新建本地文件。
- 用 [内容蓝图](../assets/design-description.txt) 整理上述章节；沿用资源契约的用途、设计/实现状态、依赖、设计依据和实际确认记录，必要时简述验证限制。长章节按需拆为有独立 ID 的小资源，由总览定向链接。
- 精确值优先引用项目的真实变量、样式、token 和组件说明；正文中的必要数值写清语义、单位、模式/渠道并保持一致，不建立另一套独立数值表。文件级 ID 与节点 ID 分开记录；需要核对实现时由 Agent 从入口仓库链接按需查证，Figma 正文不附源码路径、符号或 commit。
- 按 [文档排版约定](work-templates.md#文档排版与可读性) 使用标题、正文、列表和真实链接；不把 YAML 或 Markdown 标记原样当作可读版式。这里描述产品 UI，`documentation/work-templates` 描述文档自身的字体与排版，二者分开维护。
- 用户已有 `DESIGN.md` 时将其作为项目来源核对；与代码/Figma 冲突时列明版本、范围和已确认决策，遵循现状基线与待实现设计的区分，不因文件名就判为唯一权威。只有用户要求创建或导出文件时才按当时的完整上游格式处理；Figma 适配本身不宣称能通过上游 CLI 校验。

## 写入与检查

Init 把具体描述与来源纳入设计风格模块提案；Design 先按需读取，选定方案后只修订获准增量。保留已确认但尚未实现的风格演进和对应需求来源。

按章节检查：接手者能否据此作视觉判断，是否解释用途和理由，资源引用与精确值能否核对，正反例是否可执行，候选/未核实内容是否清楚。同步检查真实截图和文本读取；章节齐全或 token 完整都不能单独证明设计语言描述合格。
