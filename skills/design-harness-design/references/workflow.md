# Design：从项目依据到可选择方案

## 1. 从入口按需读取

按 [上下文契约](context-loading.md) 找到 Harness，先读入口中的项目边界、全局约束、有效版本与模块目录。结合新需求选择相关模块概览，再读匹配资源及必要依赖。向用户简述采用的关键依据和仍缺少的事实，不倾倒整份知识库。

对可能过时的实现事实，用入口中的代码映射核对相关代码。适用范围、已确认设计和当前实现分开判断。现有规范不能解答的新问题，留给访谈；不得把通用指导假装成项目已确认规则。

## 2. 动态访谈，达成整体理解

按 [访谈机制](interview.md) 一次解决一个高影响问题。对话承载已核实事实、已确认决策、交由 AI 决定的事项、未决问题，以及留给多方案比较的差异。

需求成熟时不从头问固定问卷。访谈中可提供流程图、文字线框或临时草图，帮助用户作决定；这些不是正式 Figma 方案，也不写回 Harness。

当目标、范围、约束、验收与比较方向明确，汇总具体共同理解，请用户整体确认。该确认同时明确正式设计的页面范围、方案差异和输出深度。已有明确批准同一总结时直接继续。用户未回复不是确认。

## 3. 在本次需求的独立 Page 生成方案

确认后创建需求 Page；本需求已有 Page 则继续。命名沿用项目习惯，可用 `需求 / 短名称 / 日期`。不要在 Harness Page 堆放所有候选稿。

使用 [需求 Page 蓝图](../assets/requirement-page.txt) 安排已确认摘要、方案对比、各方案关键页面、必要状态与交互说明。沿用项目原稿的展示方式：标题条、分组、编号、连接线或说明卡按已有习惯复用，避免套用插件的统一视觉风格。

通常制作 2–3 个有意义的方案，以已确认的比较轴决定数量与差异。每个方案解决同一目标、覆盖同一核心场景，明确主张、收益、代价与适用条件。不要用改颜色、圆角或文字替换冒充 UX 差异，也不要重新打开访谈已锁定的决策。若约束只剩一种可行路径，解释事实并先与用户调整比较范围。

按 [Figma 操作](figma-operations.md) 引用项目变量、组件实例与模板。仅对本需求必要的缺口建立新资产，并标明“候选设计”；它们暂留需求 Page，不自动变成全项目规范。

默认深度是关键页面、必要状态和交互说明。只有操作顺序、跳转、反馈时机等难以靠静态稿比较时，才补可点击原型。需要动态运行验证的行为应单独列出。

## 4. 生成过程中评价，修正后供用户选择

按 [检查标准](evaluation.md) 检查任务路径、状态、项目规则、资产复用、布局、文案和平台适配。按 [Impeccable 加载与适配](impeccable.md) 读取并应用上游最新相关指导。

回读节点及属性，截图检查目标尺寸下的渲染。对授权范围内可修正的问题直接修正，再复核受影响部分；不要重复做无关全量评审。工具无法读取或截图时如实标为未核验，不声称通过。

在需求 Page 和对话中给出方案链接、差异、推荐及理由、仍需验证的风险。问题应具体到节点/状态/任务结果；评价不做百分比完成度或综合审美分。

用户调整要求时保留仍有效的决策，必要时再访谈关键新问题，然后迭代对应方案。选择前不把某候选方案作为 Harness 默认规范。

## 5. 选定、确认增量、回写

记录用户实际选择；组合方案则明确组合后的设计。按 [知识更新](knowledge-update.md) 按模块展示变更前后、来源、影响与实现状态。用户确认具体增量后更新 Harness 资产、概览、入口和需求索引。

保持需求 Page 为决策与方案的出处；Harness 只沉淀已批准的规则、可复用资产和指向需求的索引。完成后报告选定方案、实际回写和待实现事项；不自动修改代码或宣布产品已实现。
