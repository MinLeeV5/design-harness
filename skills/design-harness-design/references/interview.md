# 需求访谈：一次解决一个关键不确定性

把 brainstorming 的展开与 grilling 的追问结合，目标是逐步确认任务、主流程、分支和视觉表达。访谈贯穿设计过程；不要执行固定问卷，也不依赖外部访谈 Skill 才能运行。

## 先判断输入成熟度

| 用户已有内容 | 从哪里开始 |
| --- | --- |
| 模糊想法/问题感受 | 目标用户在什么情境下要完成什么、目前受阻在哪里 |
| 已有任务和业务流程 | 最影响方向的范围、约束、状态和成功标准 |
| 成熟方案/历史讨论 | 先继承明确决策，检查高影响缺口、证据冲突和边界情境 |
| 明确的小改动 | 核实影响范围与验收即可，避免重做全套访谈 |

先从已加载的项目知识和相关代码找事实。不要问用户代码中已有几个状态、字号是多少、资源在哪。事实冲突先查版本/渠道，再问用户希望采用哪个取舍。

## 每轮怎么问

1. 选择当前最影响用户任务、范围、风险或方案结构的一项不确定性。
2. 简述已知依据，提出**一个问题**，给推荐及原因。选项应表达真实取舍，不把推荐包装成唯一合理答案。
3. 接收回答后更新共同理解；只有该答案的关键后果仍不清楚时追问。否则进入下一个高影响问题。

根据问题选择形式：

- **开放式**：目标尚不清晰。先给适度的推荐切入点，不硬列 A/B/C。例：“建议先看最常失败的一步，因为它决定改动范围；用户通常在哪一步卡住？”
- **取舍式**：方向可以比较。例：“更希望优先快速重试，还是先解释故障原因？我建议先给可恢复操作，因为用户正在进行中的任务对时间敏感；代价是诊断信息需要次级入口。”
- **情境式**：压力测试已有方向。例：“刚提交时断开连接，回来后可能已经成功。建议先查询结果再允许重试，避免重复操作；这种等待方式是否符合现场预期？”

这些是示例，不是预设用户业务。避免一轮塞入角色、状态、文案和交付方式等多个独立问题；也不要把每个视觉细节都升级成用户决策。

## 对话中的工作记忆

随回答维护精简摘要，仅在有意义的检查点向用户展示：

- 已核实事实：来源、适用范围及尚未核实的局限。
- 已确认决策：用户实际选择及原因；不能推断未选择的答案。
- 已委托事项：用户明确让 AI 决定的内容与边界。
- 未决问题：仍会影响方向或验收的事项。
- 留给局部比较：当前尚未确定的导航、信息展开或操作方式；默认一套主方案，选定后并回。

这些内容留在对话，不要求 `brief.md`、`run.json`、OpenSpec 提案或其他本地工件。不用置信度、完成百分比或问题数量衡量准备程度。

进度更新说清“当前阶段、已确认路径、下一条分支或最大不确定性”。用户临时提问时先回答，再延续当前访谈。恢复新会话时优先使用已有对话摘要和已确认的需求 Page；缺少关键确认记录才补问，不编造历史决定。

## 分阶段访谈

| 阶段 | 当前要解决的决定 | 推进依据 |
| --- | --- | --- |
| 整体需求与流程骨架 | 任务、入口、结果、参与端、范围与主分支关系 | 需求与骨架已确认；可在同一次具体确认中完成 |
| 主流程原型 | 当前步骤的操作方式、跳转、返回和关键反馈 | 展示可点击原型并走查，主流程交互获确认 |
| 当前分支 | 触发条件、恢复/退出、与主流程的衔接 | 当前分支确认后再展开下一条；已委托内容直接处理 |
| 视觉细化 | 信息表达、必要的新资产方向及仍影响体验的取舍 | 交互已确认；改变交互则回到对应决定 |

先展示可审阅的流程或原型片段，再问一个关键问题。AI 自行核实事实、处理已委托细节和修复范围内缺陷，不逐个按钮、图标索要确认。阶段确认可承接已有明确批准，不能用用户沉默代替。

## 草图与收敛

文字线框、流程图或临时低保真图可帮助访谈。标明它们用于讨论，不能未经确认写成正式 Figma 方案或项目规范。若用户明确要求提前把特定草图放进 Figma，按该授权范围执行，仍不视作整体需求已确认。

当以下内容足以支撑方案，就停止继续收集问题：

- 用户、任务目标、使用情境与成功标准；
- 本次范围、主路径及必要的异常/恢复；
- 项目约束与实际实现边界；
- 主方案的确定部分及需局部比较的交互；
- 主流程、分支与可点击原型的本次覆盖范围，以及纯视觉小改动的简化依据。

汇总上述内容、已委托项与尚不能验证的假设，请用户整体确认。保留给方案比较的差异不属于阻塞问题。对关键事实的猜测或用户尚未决定的重大取舍不能悄悄标成委托。

用户确认后，在需求 Page 附精简摘要并进入流程骨架、主流程和分支，不直接跳到视觉精稿，不补写本地 brief。后续持续访谈尚未解决的交互；已确认部分只因新事实、矛盾或范围变更重新讨论。
