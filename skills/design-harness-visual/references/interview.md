# 视觉目标与方案对比访谈

访谈贯穿 [视觉工作流](workflow.md)，每次只问一个问题，并给出推荐和具体理由。先承接上游交互与项目视觉规范；可从现有资产查询的事实自行核实，业务需求不重新访谈。

## 出方案前

先确认本次最希望改善的视觉结果，以及项目规范内允许探索的范围。例如“优先让设备状态一眼可辨，还是突出当前主要操作”，给出结合任务情境的推荐。沿答案明确比较依据与代表画面范围，不要求用户重新填写完整需求问卷；已有明确目标用简短汇总确认，小修改同样参与。

目标与边界明确后再制作代表方案。不同方向围绕同一目标和内容展开；用户没有指定审美词或参考图不代表无法探索，也不将 Agent 的风格偏好写成用户决定。

## 围绕画面比较

先展示本轮实际代表画面，说明每套优先解决什么、差异、收益与代价，给出推荐及理由。然后只问当前最影响选择的一项取舍；结合画面定位讨论信息层级、分组或图形表达，不一次要求回答配色、字体、插画与布局的全部偏好。

明确记录用户选择的主方向及可融合的局部内容。回答含糊时只澄清影响整合的部分，不自行把“都不错”解读为选定或自由混合。所有方案均不合适时，定位不满足目标的原因，再修订代表画面；不能跳过选择直接铺开全部页面。

## 收敛与恢复

将用户选择落实为一份一致的整合代表稿，围绕实际画面确认该版本，然后按工作流完整展开。未混合时直接呈现选定代表稿；用户已明确确认同一版本则沿用，不为相同决定多设一道审批。偏好片段、主方向、整合代表稿和完整交付的确认范围分别记录。

每个实际决定写入本阶段 [交接记录](handoff.md)，以 [视觉蓝图](../assets/visual-delivery.txt) 保存当前步骤、真实方案链接、选择理由、融合内容与未决项；不复制整段对话。同一项需求跨任务或中断恢复时从已有决定继续，不因上下文压缩重新头脑风暴。

发现问题涉及操作语义、状态、导航或恢复方式时，说明位置、影响及建议，由用户决定是否返回交互阶段。视觉访谈不能替代上游交互决定。
