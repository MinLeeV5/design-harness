# Skill 维护指南

本文用于维护通用插件的流程、知识表达、运行资源与分发约定。任务命中哪个主题，就读取对应章节及其指向的阶段文件；不要求全量加载四个 Skill。公开 Skill 的运行资源仍随各自目录携带，不引用本维护文档。

## 设计流程与知识

### 阶段行为与交接

四个入口只负责自己的阶段，不恢复自动串联的 Design 总入口。维护某阶段前，读取下表对应工作流及其引用的访谈、交接和评价文件：

| 阶段 | 维护时必须保持的边界 | 执行依据 |
| --- | --- | --- |
| Init | 先整理存量上下文，再补代码已有而设计缺失的内容；逐模块共创知识意图、适用边界和复用取舍，修订具体提案并确认后生成；沿用同范围已有授权 | [Init 工作流](../skills/design-harness-init/references/workflow.md) |
| 交互 | 先确认流程和关键草图，再逐页制作一套主方案；必经等待先作最小表达，主流程各页通过并串联确认后，才逐页补分支、逐种补单页状态；局部备选也逐项放行 | [交互工作流](../skills/design-harness-interaction/references/workflow.md) |
| 视觉 | 承接已确认交互；先访谈，再逐套逐页制作 2–3 套代表候选，齐备后比较选择；候选制作验收不等于最终选定，整合代表范围确认后仍逐页、逐状态展开，小修改也适用 | [视觉工作流](../skills/design-harness-visual/references/workflow.md) |
| 知识回写 | 只写批准的知识增量，保留已确认待实现的设计状态；本阶段完成后停止 | [回写工作流](../skills/design-harness-writeback/references/workflow.md) |

共创与制作单位复用 [逐题共创与逐项门禁](../README.md#逐题共创与逐项门禁)，不在本指南维护第二份步骤。修改时重点核对：已有决定与同范围授权直接承接；取舍回答、稿件验收和下一项授权分别记录；只修改当前项不放行后续项；本项工具调用和错误修复不重复审批；目标页未生成时登记待补连接，不预建下一页。

行为明确的小修改可直接进入适用阶段，进入视觉后仍确认目标并比较代表方案。阶段间靠真实交付物与确认结论交接；完成后由用户控制下一阶段和是否新建任务。下游发现上游问题时，只提出影响与建议，不擅改已确认行为或记录。

恢复与记录内容复用 [交接与恢复](../README.md#交接与恢复) 及当前阶段的 `references/handoff.md`：先读可见交接和必要产物，核对实际状态、上游版本与未完讨论，只补问影响当前工作的缺口。记录真实结论、理由、变化及验收/放行，不复制对话全文或强制本地流程文件；同一任务切换 Skill 不清空上下文。

### Figma 知识与文档

使用方项目的设计知识放在其 Figma Harness 页面，每次需求使用独立页面。项目设计规范优先于通用指导；还原现有行为时优先采用已核实的当前代码，影响决策的冲突展示依据并交由用户选择。当前代码基线与已确认的新设计分开保留，后者可标待实现。具体契约见 [上下文契约](../skills/design-harness-init/references/context-contract.md)。

Figma 面向设计师，用产品行为、设计规则和状态表达知识。Contract 1 入口只保留一条经 remote 核实的仓库链接；源码路径、符号、commit、拉取命令和核查日志留在 Agent 的按需调查中，不写入正文、技术附录或隐藏数据。项目上下文聚焦产品定位、用户任务、使用环境、渠道差异和业务边界；具体页面行为归布局、组件或场景，以索引关联，避免重复展开。

入口和索引用可见原生文本逐层读取，不依赖隐藏 `pluginData` 或全文件扫描。变量与样式是文件级资产；获准编辑一个 Page 不代表获准修改整个文件。文档使用原生富文本表达标题、段落、列表和链接层级，沿用项目样式并检查实际整体与局部截图；保留语义 TEXT、可见仓库链接和真实 Figma 定位，不全篇同字号平铺，也不生成隐藏正文副本。产品界面与评审说明优先图形配必要短文，保留标签、操作后果、规则和真实定位。

工作模板复用 [文档与原生资产](../README.md#文档与原生资产)：场景流程、方案对比、规范资源采用统一结构；项目文档配置和原生模板引用登记在 Figma 设计风格模块，产品 UI 模板独立维护。蓝图不能冒充已生成的原生资产，也不写入具体项目文件、节点或业务名称。

设计语言描述按 [设计描述方法](../skills/design-harness-init/references/design-description.md) 关联视觉意图、使用理由和精确 token，维护时按需读取 Google DESIGN.md 上游最新相关规范与理念，项目规范优先；内容沉淀在 Figma 设计风格模块，不强制另建本地 `DESIGN.md`。

### Library 与视觉资产

Init 在现有模块登记适用 Library 来源和复用规则，视觉阶段按需复核、检索。优先复用适用的项目/团队资产，区分“未找到”和“无法查询”；新增来源或风格、源库管理和文件级变更遵守具体授权。查库和复用不自动授权启用、发布或修改源库。具体方法见 [视觉资产选择](../skills/design-harness-visual/references/visual-assets.md)。

缺口分别采用成熟矢量图标、可编辑示意图或情境插画；这些是按需加载的内部参考，不新增公开 Skill。图标同时检查形状识别与语境含义；插画先明确表达目的，再制作代表样图、扩展必要系列，并做实际版面验收。社区体系参数不自动成为项目规范。维护对应方法时只读相关的 [图标参考](../skills/design-harness-visual/references/iconography.md) 或 [插画参考](../skills/design-harness-visual/references/illustration.md)。

## Skill 结构与运行

每个 Skill 自包含并渐进加载：`SKILL.md` 入口简短，执行文档与评价标准放在自己的 `references/`，产出蓝图放在 `assets/`，运行助手放在 `scripts/`。不能引用插件根目录或另一个 Skill 的运行文件。

四个 Skill 各自维护本阶段工作流与评价。共享文件按实际使用方同步并校验，不为同步复制无关阶段流程：

| 使用方 | 随入口携带的共享内容 |
| --- | --- |
| 全部四阶段 | 读取助手、连接器适配、交接协议/蓝图、文档模板和原创许可 |
| 交互、视觉、回写 | 上下文读取约定 |
| Init、视觉 | 视觉资产方法、设计语言描述及适用来源/许可 |
| 交互、视觉 | 通用 UX 路由与适用许可 |

实际分组由 [共享资源校验](../scripts/validate.js) 中的 `SHARED_SKILL_GROUPS` 维护。交互不携带插画生成或回写流程，知识回写不携带设计访谈或第三方设计指南。

Figma 读取助手使用无外部依赖的 JavaScript，运行于 Plugin API 环境；Skill 内路径相对于各自目录。根目录开发脚本与测试使用 Node.js 22+、ESM 和 npm，测试使用内置 `node:test`，ZIP 使用开发依赖 `fflate`。开发依赖不进入分发包，也不成为 Skill 运行依赖。实际命令和安装方式见 [开发与打包说明](../README.md#安装与团队分发) 及 [验证范围](validation.md)。

连接器操作按 [工具衔接](../skills/design-harness-init/references/figma-operations.md) 先发现工具和实际参数，再探测连接并核对目标文件；按需求选择专用工具或脚本执行工具，支持 figma-console-mcp 与 `use_figma`，不将任一连接器设为硬依赖。工具注册不等于连接成功；Console 专用工具可能使用活动文件，`figma_execute` 的 `fileKey` 不会切换其他工具的活动目标，跨工具前须核对同一文件与 Page。超时先查实际结果，再补缺，不能换连接器重放整个写入。

Evaluation 嵌入各自工作流，检查真实资产与渲染结果。原型连接配置、实际点击和产品运行分别验证；脚本不能证明设计质量、用户批准或实际运行行为。模拟 API 与真实 Figma 的验证边界以 [验证说明](validation.md) 为准。

## 外部来源与许可

第三方来源和许可放在实际使用它们的 Skill 中，保留上游许可证和声明。需要外部指导时先定位具体问题，只读取上游默认分支最新的相关段落及必要上下文，不固定 tag、commit 或维护版本锁；项目规范和已确认的工作方式优先。获取失败时如实说明，不能把本地摘要称为最新上游；维护适配内容时同时核对上游最新许可。

区分本地适配、在线阅读入口和实际素材，公开可读不代表允许复制分发。Lucide 许可随包保留；IBM、Atlassian 和 NN/g 仅作为在线阅读来源，不复制其手册或图形，也不以相邻仓库或通用 Skill 的许可代替素材许可。边界见 [视觉指导声明](../skills/design-harness-visual/third-party/visual-assets/NOTICE.md)。

Impeccable 与 UI/UX Pro Max 按当前问题补充指导并适配实际平台，不引入完整审计、安装、持久化或多 Agent 流程，也不将其作为 Skill 运行依赖。来源按当前阶段的 `references/sources.md` 发现，例如 [视觉来源](../skills/design-harness-visual/references/sources.md)。

## 版本与分发

发布版本时同步插件清单、`package.json` 和锁文件，使用不带本地缓存后缀的 SemVer；`+codex.*` 只用于本地调试。发布记录维护在 GitHub Release，不恢复已删除的旧版迁移资料。用户文案保持中文和可直接阅读的 UTF-8，刷新缓存版本后也保留中文原文。

仓库 [marketplace 入口](../.agents/plugins/marketplace.json) 使用稳定名称 `design-harness`，以 `./` 指向根目录插件；GitHub 安装跟随明确的 Git 引用。ZIP 外层 marketplace 从同一入口派生，将路径调整到 `./plugins/design-harness`，避免元数据漂移。

安装依赖使用 `npm ci`；校验、测试和打包复用 [README 命令](../README.md#安装与团队分发)。打包使用新输出目录，保持可重复构建、SHA-256 和拒绝覆盖；随包携带 `package.json` 与锁文件，排除依赖目录和临时数据。分发方式变更时，在全新路径验证打包与解压，并分别验证仅复制单个 Skill 后的引用完整性；模拟 API 测试与真实 Figma 验证分开报告。

插件品牌图形与生成提示词维护在根目录 `assets/`，随 Git 和 ZIP 分发，不是 Skill 运行依赖。图标保持四个色块和透明 H 留白，浅深共用同一图形；修改时按 [品牌说明](../assets/README.md) 与 [验证范围](validation.md) 核对清单引用、浅深背景、小尺寸渲染，以及解压后的资源字节一致性。
