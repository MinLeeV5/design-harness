# 选择方案后的知识更新

项目知识随项目成长。本版本只维护当前项目已确认的具体增量，不自动跨项目学习，不把候选方案晋升为通用规范。

## 分开记录设计与实现

| 事实 | 写法与使用方式 |
| --- | --- |
| 从当前代码核实的现状 | 现状基线；代码已实现；附 revision/范围与静态或运行核对方式 |
| 本次比较中的新方案 | 候选设计；不能作为其他需求默认约束 |
| 用户已选择且确认沉淀的新规范/资产 | 已确认设计／待实现；适用于确认过的目标范围 |
| 后续核对代码确已落地 | 已确认设计／代码已实现；附新 revision 与核对证据 |
| 尚不能核实或已明确被取代 | 未核实，或已取代并指向有效版本；保留必要历史来源 |

设计状态、实现状态与验证方式是三个不同维度。静态读代码不等于运行验证；Figma 截图检查不等于产品已实现。

倾向当前代码的原则用于还原现状、解决未决历史分歧；不能覆盖用户已批准的未来设计。Design 根据目标版本选择有效约束，同时知道当前实现差距。Init 遇到旧实现，不得把“已确认／待实现”倒退成错误稿。

## 先给具体增量，再确认

用户选定方案后，按受影响模块分组展示：

| 字段 | 内容 |
| --- | --- |
| 变更前 → 变更后 | 具体规则、token、组件属性/状态、模板或场景；无变化的模块不列 |
| 来源与适用范围 | 选定需求 Page / 方案节点，适用平台、渠道、版本与任务 |
| 回写方式 | 新增、修订、取代，或仅增加需求索引；实际节点/文件级资产范围 |
| 影响 | 已有资产与场景是否受影响；是否保留当前实现基线 |
| 状态 | 已确认设计／待实现，或有充分依据的已实现；说明核对方式 |

使用 [增量蓝图](../templates/writeback-delta.txt) 组织对话中的提案，必要时在需求 Page 呈现。没有可复用变化时只提出选择记录与需求索引，不为了回写制造新规则。

用户确认这个具体增量后才更新 Harness。可以一次明确批准展示出的若干模块，也可以分别决定；不要从“我选 B”推定用户接受尚未展示的全局规范改动。此前已明确批准同一增量和范围时引用确认直接执行，不重复询问。

## 更新资产与索引

1. 检查稳定资源 ID、旧资产引用和依赖。新设计会影响当前实例时，默认新建可辨版本/变体并明确目标范围，除非用户明确批准原位替换。
2. 将已批准的可复用内容整理到 Harness；沿用已有有效组件、变量和模板，保持需求稿对已批准资产的引用。若复制/移动组件会影响实例，先读依赖，再选择安全方式并核对链接；不要假设 clone 会自动迁移所有实例关系。
3. 保留来源方案和当前代码基线。全局 token/主组件修改须在确认的文件级范围内，不以“回写知识”为由影响未授权原稿。
4. 更新资源说明、模块概览、入口的有效基线/待实现索引及需求索引。新资产先生成，再使用真实 ID 建索引。
5. 回读状态与依赖，检查截图和实例绑定。操作部分失败时只报告真实完成部分，回读后续做未完成项，避免重复资产。

用户暂缓回写时，保留其选定方案与对话结论，报告尚未沉淀的具体部分。代码实现后的再次对齐按相关模块走增量 Init；未经核实不能自动把“待实现”切成“已实现”。
